     1→# Web Pro Record — Worklog

     3→## Project Status (Initial Build Complete)
     4→
     5→**App:** Web Pro Record — a fully client-side, bilingual (EN/AR) screen + webcam + microphone recorder built on Next.js 16. No backend, no AI APIs, no uploads. All recording happens in the browser via native Web APIs (`getDisplayMedia`, `getUserMedia`, `MediaRecorder`, Canvas `captureStream`, `AudioContext`).
     6→
     7→### Architecture
     8→- `src/app/layout.tsx` — Geist + Cairo (Arabic) fonts, metadata, ThemeProvider (next-themes, dark default)
     9→- `src/app/globals.css` — custom emerald theme (light/dark), Arabic font wiring, recorder styles (rec-pulse, hero-aura, dot-grid, custom scrollbar)
    10→- `src/lib/i18n.ts` — full EN/AR dictionary (~150 keys), `translate()`, `isRtl()`
    11→- `src/lib/recorder-utils.ts` — formatDuration/Bytes/Resolution, `pickMimeType()` (vp9→vp8→h264→webm→mp4), `detectFeatures()`, `enumerateDevices()`, `computeCanvasSize()`, `qualityToVideoBitrate()`, `drawRoundRect()`
    12→- `src/hooks/use-recorder.ts` — the core recorder hook (state machine + media logic). Accepts a `canvasRef` param (kept out of return to satisfy `react-hooks/refs`). Manages: idle webcam preview loop, countdown, screen capture, mic, system-audio detection, canvas compositing (screen base + webcam overlay with shape/position/size/margin/border/shadow + optional watermark), AudioContext mixing (mic + screen audio → MediaStreamAudioDestinationNode), MediaRecorder with negotiated MIME + configurable bitrates, chunk collection, onstop blob/URL building + track cleanup, screen-share-ended handling, pause/resume timer, mic level meter (AnalyserNode), full reset/record-again/download/copy-details.
    13→- `src/components/recorder/` — header, hero, control-panel, live-preview, final-recording, help-section, footer
    14→- `src/app/page.tsx` — orchestrator: lang state + `document.dir` sync, canvasRef ownership, error/warning → toast, browser-recommendation banner (non-Chromium), unsupported blocker, floating recording status chip, sticky footer (`min-h-screen flex flex-col` + `mt-auto`)

   430→#### SEC-001 — CRITICAL — Caddyfile open reverse-proxy (SSRF)
   431→- **File:** `Caddyfile:6-13`
   432→- **Problem:** The Caddyfile accepts any request with query parameter `?XTransformPort=<port>` and reverse-proxies it to `localhost:<port>`. An external attacker can craft URLs like `https://<deployed-host>/?XTransformPort=5432` to reach PostgreSQL, `XTransformPort=6379` for Redis, `XTransformPort=9000` for PHP-FPM, internal admin panels, the Prisma SQLite RPC, metadata services, etc. — any TCP listener on the host.
   433→- **Root cause:** The `@transform_port_query` matcher + `reverse_proxy localhost:{query.XTransformPort}` block trusts a user-controlled query parameter as the upstream target with no allowlist.
   434→- **Impact:** Full SSRF — attackers can pivot into every local service, exfiltrate database contents, hit cloud-metadata endpoints (169.254.169.254), scan internal network, bypass firewalls. This is the single most severe finding in the audit, and it is in the deployment config that ships with the repo.
   435→- **Recommended fix:** Remove the dynamic-port block entirely, or replace it with an explicit allowlist (e.g. `:3000`, `:3003` only). At minimum, restrict to known safe ports:
   436→  ```caddyfile
   437→  @allowed_port query XTransformPort=3000
   438→  query XTransformPort=3003
   439→  handle @allowed_port { reverse_proxy localhost:{query.XTransformPort} }
   440→  ```

   444→#### SEC-002 — HIGH — No Content-Security-Policy or security headers
   445→- **File:** `next.config.ts:3-10`
   446→- **Problem:** `next.config.ts` defines only `output: "standalone"`, `typescript.ignoreBuildErrors`, and `reactStrictMode: false`. There is **no `headers()` configuration**, so the deployed app ships with **no** `Content-Security-Policy`, no `X-Frame-Options`/`frame-ancestors`, no `X-Content-Type-Options: nosniff`, no `Referrer-Policy`, no `Permissions-Policy`. The app calls `getDisplayMedia`/`getUserMedia` — without a `Permissions-Policy` that explicitly allows them only on this origin, third-party iframes/ embedders can attempt to frame the page and request camera/mic/screen.
   447→- **Root cause:** Default Next.js config doesn't add security headers; developer must opt in.
   448→- **Impact:** (1) If any XSS is ever introduced (now or by a future dependency), there is no CSP to contain it. (2) Clickjacking — page can be iframed by attackers. (3) MIME-sniffing attacks. (4) Permission prompts can be triggered from framed contexts.
   449→- **Recommended fix:** Add a `headers()` block to `next.config.ts`:
   450→  ```ts
   451→  const nextConfig: NextConfig = {
   452→    async headers() {
   453→      return [{
   454→        source: "/(.*)",
   455→        headers: [
   456→          { key: "Content-Security-Policy",
   457→            value: "default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; media-src 'self' blob:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'" },
   458→          { key: "X-Frame-Options", value: "DENY" },
   459→          { key: "X-Content-Type-Options", value: "nosniff" },
   460→          { key: "Referrer-Policy", value: "strict-origin-when-cross-origin" },
   461→          { key: "Permissions-Policy",
   462→            value: "camera=(self), microphone=(self), display-capture=(self), geolocation=(), clipboard-write=(self)" },
   463→        ],
   464→      }];
   465→    },
   466→  };
   467→  ```

   501→#### SEC-005 — MEDIUM — Watermark logo upload accepts SVG (script-injection footgun)
   502→- **File:** `src/components/recorder/control-panel.tsx:642`
   503→- **Problem:**
   504→  ```tsx
   505→  <input type="file" accept="image/png,image/jpeg,image/svg+xml" ... />
   506→  ```
   507→  SVG files can contain `<script>` tags and event handlers (`onload`, `onerror`). The uploaded file is read via `FileReader.readAsDataURL` (`control-panel.tsx:653`) and stored as `watermarkLogoDataUrl`. Currently the data URL is consumed in two XSS-safe ways: (1) `<img src={dataUrl}>` at `control-panel.tsx:675` (img tags don't execute SVG scripts), and (2) `new Image()` + `ctx.drawImage()` at `use-recorder.ts:368,730` (canvas drawImage doesn't execute scripts either). **Today this is safe**, but it is a footgun — any future code path that renders the data URL via `<embed>`, `<object>`, `<iframe>`, `<a target=_blank href={dataUrl}>`, `fetch(dataUrl).then(r => r.text())` then `innerHTML`, or top-level navigation would execute attacker-controlled script in the app origin.
   508→- **Root cause:** SVG is included in the accept list without a clear need (the watermark feature wants raster logos).
   509→- **Impact:** Latent XSS — depends on future code changes. Also, SVGs can carry XXE payloads that affect some parsers (not the browser's `<img>` loader, but defense-in-depth is wise).
   510→- **Recommended fix:** Drop SVG from the accept list:
   511→  ```tsx
   512→  accept="image/png,image/jpeg,image/webp"
   513→  ```
   514→  And validate the data URL prefix in the `onload` handler:
   515→  ```ts
   516→  reader.onload = () => {
   517→    const dataUrl = reader.result as string;
   518→    if (!/^data:image\/(png|jpeg|webp);base64,/.test(dataUrl)) return;
   519→    if (dataUrl.length > 1_500_000) { toast({ description: "Logo too large (max 1 MB)" }); return; }
   520→    rec.updateSettings("watermarkLogoDataUrl", dataUrl);
   521→  };
   522→  ```

   544→#### SEC-008 — MEDIUM — localStorage prefs JSON.parse has no schema validation
   545→- **File:** `src/hooks/use-recorder.ts:195-206, 353-357`
   546→- **Problem:**
   547→  ```ts
   548→  function loadPrefs(): Partial<PersistablePrefs> | null {
   549→    const raw = window.localStorage.getItem(PREF_KEY);
   550→    if (!raw) return null;
   551→    const parsed = JSON.parse(raw);
   552→    if (!parsed || typeof parsed !== "object") return null;
   553→    return parsed as Partial<PersistablePrefs>;   // ← no field-type validation
   554→  }
   555→  // ...
   556→  const prefs = loadPrefs();
   557→  if (prefs) {
   558→    setSettings((prev) => ({ ...prev, ...prefs }));   // ← blind spread
   559→  }
   560→  ```
   561→  Any value (correct type, wrong type, extra fields, malicious `__proto__`-like keys) is accepted and spread over `DEFAULT_SETTINGS`. Downstream consumers assume typed fields:
   562→  - `drawWatermark` at `use-recorder.ts:702` calls `s.watermarkText?.trim()` — crashes if `watermarkText` is a number.
   563→  - `Math.round(h * s.watermarkLogoSize)` at `:712,723` returns `NaN` if `watermarkLogoSize` is a string.
   564→  - Slider components receive non-number values and may render NaN.
   565→  A malicious script on the same origin (e.g., via an XSS in a future dependency, or another app hosted on the same origin) could plant `localStorage.setItem("wpr-prefs-v1", JSON.stringify({watermarkText: 12345, quality: "4320", frameRate: "999"}))` to crash the recorder on next load — a persistent client-side DoS.
   566→- **Root cause:** `JSON.parse` + bare cast without runtime validation.
   567→- **Impact:** Persistent client-side DoS via crafted localStorage; potential crashes if attackers can write to localStorage.
   568→- **Recommended fix:** Validate each field by type and range before merging, e.g.:
   569→  ```ts
   570→  function loadPrefs(): Partial<PersistablePrefs> | null {
   571→    try {
   572→      const raw = window.localStorage.getItem(PREF_KEY);
   573→      if (!raw) return null;
   574→      const p = JSON.parse(raw);
   575→      if (!p || typeof p !== "object" || Array.isArray(p)) return null;
   576→      const out: Partial<PersistablePrefs> = {};
   577→      if (typeof p.watermarkText === "string") out.watermarkText = p.watermarkText.slice(0, 200);
   578→      if (typeof p.watermarkOpacity === "number") out.watermarkOpacity = clamp(p.watermarkOpacity, 0.1, 1);
   579→      if (typeof p.watermarkSize === "number") out.watermarkSize = clamp(p.watermarkSize, 0.01, 0.06);
   580→      if (typeof p.watermarkLogoSize === "number") out.watermarkLogoSize = clamp(p.watermarkLogoSize, 0.02, 0.15);
   581→      if (["text","logo","both"].includes(p.watermarkMode)) out.watermarkMode = p.watermarkMode;
   582→      if (["720","1080","1440","native"].includes(p.quality)) out.quality = p.quality;
   583→      if (["24","30","60"].includes(p.frameRate)) out.frameRate = p.frameRate;
   584→      // ... and so on for each persistable field
   585→      return out;
   586→    } catch { return null; }
   587→  }
   588→  ```

   778→#### CODE-001 — CRITICAL — `enableWebcam()` overwrites stream ref without stopping previous tracks (memory leak + camera light stuck)
   779→- **File:** `src/hooks/use-recorder.ts:620-651`
   780→- **Problem:**
   781→  ```ts
   782→  const enableWebcam = useCallback(async () => {
   783→    setError(null);
   784→    try {
   785→      const stream = await navigator.mediaDevices.getUserMedia(constraints);

   849→#### CODE-005 — HIGH — Countdown timer is uncancellable; recursive `setTimeout` fires after cancel
   850→- **File:** `src/hooks/use-recorder.ts:1188-1207`
   851→- **Problem:**
   852→  ```ts
   853→  const runCountdown = useCallback(
   854→    (seconds: number) =>
   855→      new Promise<void>((resolve) => {
   856→        setCountdownValue(seconds);
   857→        setStatus("countdown");
   858→        let remaining = seconds;
   859→        const tick = () => {
   860→          setCountdownValue(remaining);
   861→          if (remaining <= 0) { setCountdownValue(null); resolve(); return; }
   862→          remaining -= 1;
   863→          setTimeout(tick, 1000);   // ← never tracked, never cleared
   864→        };
   865→        tick();
   866→      }),
   867→    [],
   868→  );
   869→  ```
   870→  The `setTimeout(tick, 1000)` handle is discarded. `cancelCountdown` (line 1865) does `setCountdownValue(null); setStatus("idle");` but the queued `setTimeout` is still pending. ~1 second later, `tick` fires again and calls `setCountdownValue(remaining)` (where `remaining` is the stale pre-cancel value), causing a phantom countdown number to briefly reappear. Worse: `startRecording` `await`s this Promise; if the user cancels mid-countdown, `runCountdown` never resolves (the only `resolve()` is at `remaining <= 0`), so `startRecording` hangs forever in the `await` — until the next `tick` eventually reaches 0 and resolves. Between cancel and that resolution, `startRecording` is suspended, but its already-captured closures hold resources.
   871→- **Root cause:** No `countdownTimerRef` to track the timeout; no rejection path on cancel.
   872→- **Impact:** (1) Phantom countdown number flashes after Escape. (2) `startRecording`'s `await runCountdown(...)` never resolves if cancelled, leaving the async function suspended. (3) If the component unmounts during countdown, `tick` still fires and calls `setState` on an unmounted component (React 18 tolerates this but it's a warning).
   873→- **Recommended fix:**
   874→  ```ts
   875→  const countdownTimerRef = useRef<ReturnType<typeof setTimeout> | null>(null);
   876→  const runCountdown = useCallback((seconds: number) =>
   877→    new Promise<void>((resolve, reject) => {
   878→      let remaining = seconds;
   879→      const tick = () => {
   880→        setCountdownValue(remaining);
   881→        if (remaining <= 0) { setCountdownValue(null); resolve(); return; }
   882→        remaining -= 1;
   883→        countdownTimerRef.current = setTimeout(tick, 1000);
   884→      };
   885→      tick();
   886→    }), []);
   887→  const cancelCountdown = useCallback(() => {
   888→    if (countdownTimerRef.current) {
   889→      clearTimeout(countdownTimerRef.current);
   890→      countdownTimerRef.current = null;
   891→    }
   892→    setCountdownValue(null);
   893→    setStatus("idle");
   894→  }, []);
   895→  ```
